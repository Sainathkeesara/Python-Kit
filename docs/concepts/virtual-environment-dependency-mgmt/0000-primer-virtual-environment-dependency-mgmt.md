# Virtual Environment & Dependency Mgmt — quick primer

> First-day notes on virtual environments and dependency management. What they are, why they matter, and the key ideas to know.

## What is it?

A virtual environment is an isolated Python installation — it has its own `python` binary, its own `pip`, and its own set of installed packages. When I activate a virtual environment, anything I install with `pip` (or `uv`) goes into that environment and doesn't affect the system Python or any other project.

Dependency management is the practice of declaring what packages your project needs and locking their versions so every install is reproducible. The two go together: virtual environments give you isolation, and dependency management tools give you control over what goes into them.

I think of it like a dedicated toolbox for each project. Instead of having one giant toolbox with every tool I've ever installed (where two projects might need different versions of the same tool), each project gets its own small toolbox with exactly what it needs.

## Why does it matter for Python?

In Python, this matters more than in some other languages because the Python ecosystem has many competing package management tools (pip, uv, poetry, conda, pipenv) and the standard library included `venv` specifically for creating virtual environments.

Without virtual environments, installing a package for one project could break another project that needs a different version of the same package. Real example I've seen: Project A needs `requests==2.28.0`, Project B needs `requests==2.31.0`. Without separate environments, I'd have to pick one version.

Dependency management tools like `uv` and `pip` handle:
- **Declaring dependencies** — Listing what packages a project needs in `pyproject.toml` or `requirements.txt`.
- **Resolving versions** — Figuring out which versions of each package satisfy all constraints.
- **Locking** — Saving the exact resolved versions so every install is identical (in `uv.lock` or `requirements.txt`).

## Key terminology

- **Virtual environment** — An isolated Python environment with its own packages. Example: `python -m venv .venv` creates one, then `source .venv/bin/activate` activates it.
- `pyproject.toml` — The modern Python project config file where dependencies and build settings are declared. Example: `[project] dependencies = ["requests>=2.28"]`.
- `uv.lock` — A lockfile generated by `uv` that records exact versions and hashes of every dependency. Guarantees reproducible installs.
- **Lockfile** — A file that pins every transitive dependency to a specific version and checksum. Enables deterministic builds.
- **Dependency resolution** — The process of finding a set of package versions that satisfy all version constraints across the dependency tree.
- **Transitive dependency** — A package that your dependency depends on. Example: if my project uses `requests`, and `requests` uses `urllib3`, then `urllib3` is a transitive dependency.
- **Marker** — A condition that controls when a dependency is installed, based on Python version, OS, or platform. Example: `importlib-metadata; python_version < "3.10"`.
- `pip-audit` — A tool that scans installed packages against known vulnerability databases and reports CVEs.

## A concrete example

Here's the workflow I use with `uv` to set up a new project:

```bash
# Create project and virtual environment in one command
uv init my-project
cd my-project

# Add dependencies
uv add requests pandas

# The above creates/updates pyproject.toml and uv.lock
# Now install everything
uv sync

# The project has its own .venv/ with requests, pandas, and their deps
# Running a script uses the env's packages
uv run python myscript.py
```

Without virtual environments, `pip install requests pandas` would install into the system Python and affect every project on the machine.

## How this connects to what's next

Understanding virtual environments and lockfiles is essential before using tools like `uv`, `pip-audit` (which scans installed packages for vulnerabilities), `pipdeptree` (which visualizes dependency trees), and `tox` (which creates temporary virtual environments for testing across Python versions).
