# How uv.lock records dependency groups, markers, and transitive dependencies

I've been reading through `uv.lock` files generated by `uv sync` and trying to understand what's actually stored in there. It's more than a flat package list.

## Dependency groups

When I run `uv add requests`, the package lands in the default group. If I add a dev dependency with `uv add --dev pytest`, it goes into the dev group. The lockfile records which group each package belongs to.

Looking at a real entry:
```toml
[package]
name = "requests"
version = "2.32.3"
groups = ["default"]
```

And for dev deps:
```toml
[package]
name = "pytest"
version = "8.3.4"
groups = ["dev"]
```

This matters because `uv sync --no-dev` skips everything in the `dev` group. The lockfile makes that decision explicit so every install is reproducible.

## Markers

Some dependencies only apply to certain platforms or Python versions. `uv.lock` records the environment markers that were resolved when the lockfile was created.

For example, `typing-extensions` might carry `requires-python = ">=3.8"` at the package level, and platform-specific markers appear inline. When I share the lockfile with a teammate on a different OS, uv uses these markers to decide what actually needs to be installed.

## Transitive dependencies

`requests` pulls in `urllib3`, `certifi`, `charset-normalizer`, and `idna` — I don't add those manually. In `uv.lock`, they appear as separate `[package]` entries with their own `dependencies` lists.

What surprised me is that `uv.lock` captures the full resolution tree, not just top-level pins. That means `uv sync --frozen` reproduces the exact same environment anywhere. With a plain `requirements.txt`, transitive resolution can still drift between machines.
